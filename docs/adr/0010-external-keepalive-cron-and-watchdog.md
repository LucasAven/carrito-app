# Keepalive comes from an external cron, with the alert in the HTTP status

Supabase pauses a Free plan project after 7 days of low activity, and the rule is not "zero requests for 7 days": the [docs](https://supabase.com/docs/guides/platform/free-project-pausing) ask for "sufficient user database activity" and say "typically a few user requests to the database each day" is enough. One Shortcut entry per work day (see [ADR-0004](./0004-siri-entry-via-shortcut-api.md)) sits at or below that line, which is why this project kept pausing while it was in daily use. An external cron now calls [`keepalive_ping()`](../../supabase/migrations/20260921120000_keepalive_ping.sql) hourly, which reads `entries` and `api_tokens` so the call counts as real user activity, and a second daily job calls `shortcut_watchdog()`, which runs the same read but **raises** when nothing has been written for five days. Splitting them into two functions is the load-bearing decision: none of the free cron services can assert on a response body (cron-job.org has no such feature on any tier, and UptimeRobot's keyword monitoring is free but its custom headers are not, so it cannot send the `apikey` header to PostgREST at all), so the only failure signal a free service can act on is the HTTP status, and putting the staleness check in a separate function keeps the watchdog as the only one allowed to fail. `keepalive_ping()` always returns 200 even when the data is stale, so a broken-Shortcut alert can never interfere with the call that keeps the project up. Both are `SECURITY DEFINER` with `execute` granted to `anon` and nothing else, per [ADR-0007](./0007-data-api-roles-get-no-default-grants.md). Staleness reads `entries.created_at` rather than `occurred_on`, because an Entry can be backdated (see [ADR-0003](./0003-new-entries-default-to-viewed-day.md)) and `occurred_on` would report stale right after a real write; five days survives a long weekend plus a Monday holiday without crying wolf. We rejected `pg_cron` inside the database, which is the most common suggestion online but is nowhere documented to count as *user* activity (Supabase's own answer on the topic tells you to call the REST API from outside) and stops with the project anyway, so it can never wake it back up. We rejected the obvious `GET /rest/v1/entries` ping, because `anon` holds no grant on the table and the request dies with `42501` before RLS is consulted, so a monitor watching only the status code sits green forever while doing nothing, which is the single most common way these keepalives fail silently. We rejected an Edge Function or `/auth/v1/health` ping (neither touches Postgres, and one reported project was paused while serving 20 Edge Function calls an hour) and the Storage-object-plus-uptime-monitor trick (egress is CDN cached, so a hit may never reach the database, and reports on whether it works are split). We rejected GitHub Actions, which would work but auto-disables scheduled workflows in public repos after 60 days with no commits, so it would quietly die and take the keepalive with it. Revisit if the project pauses again while both cron jobs are green, which would mean the request rate is not the constraint and the next step is a support ticket rather than a faster cron; the guaranteed fix is Pro, which never pauses, but there is no cheaper paid tier and $25/mo is hard to justify for one food truck. Setup steps live in [the keepalive guide](../keepalive-setup.md).
